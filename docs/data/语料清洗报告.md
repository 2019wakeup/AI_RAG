# 语料清洗报告（T15 · 域外表格剔除与碎块过滤）

> 生成依据：`data/corpus/cleaning-rules.json`（规则）+ `scripts/validate-corpus.ts`（断言）。
> 本文所有数字都可由下方命令原样复跑，**不是估算**。
> 结论：表格语料 **1,041 → 934 条**（剔除 107 条 / 24 篇域外文献），碎块下限由 10 字上调到 **30 字**。

## 1. 为什么要做

课程题目要求「选择一个明确的领域」。语料里混入了信息检索、通用机器学习、知识图谱方法类论文的表格，
它们会在检索时被当成「沥青养护材料证据」返回，直接稀释领域纯度，也让拒答判据更难成立。

清洗前的现状：`data/corpus/tables/tables.json` 共 1,041 张表、85 个题名，其中 24 篇文献属于域外方法类。

## 2. 判据：以 `sourcePath` 为键，不以 `docTitle` 为键

这是本次清洗最重要的一条设计决定。`docTitle` 在语料里是**从 PDF 抽取的题名，可能是文件名残留**，直接做关键词黑名单会同时漏判与误杀：

| 反例 | `docTitle` | `sourcePath` | 判定 |
|---|---|---|---|
| 漏判 | `sigir_main.dvi` | `120 Reciprocal rank fusion outperforms condorcet…pdf` | **域外**（RRF 是信息检索方法），但题名里没有任何可用关键词 |
| 误杀 | `degruyter_eng_eng-2022-0463 1..26 ++` | `2022-open Engineering-A review of rutting in asphalt concrete pavement.pdf` | **域内**（沥青车辙综述），题名像垃圾 |
| 误杀 | `Microsoft Word - sustainability-1167381-FC done-original.docx` | `056 Review on Machine Learning Techniques for Developing Pavement Performance Predictions.pdf` | **域内**（路面性能预测综述） |

因此规则文件以 `sourcePath` 为唯一键（1,041/1,041 条都有该字段，无缺失），`docTitle` 只作为展示名保留。

**保留的边界案例**：`Chen - 2020 - A Novel Multi-Criteria Decision-Making Model for Building Material Supplier Selection`（14 张表）
属于建筑材料选型决策，虽非沥青但仍在材料域内，**未剔除**；同类保留的还有「机器学习预测沥青性能」等把 ML 用在沥青对象上的论文——
判据是**研究对象是不是沥青/路面材料**，不是「用没用机器学习」。

## 3. 规则文件

`data/corpus/cleaning-rules.json`：

```json
{
  "version": 1,
  "minChunkChars": 30,
  "excludedDocs": [
    { "sourcePath": "…", "docTitle": "…", "category": "xgboost", "reason": "…", "tables": 4 }
  ]
}
```

- `category` 取值：`llm_agent` / `dpr` / `colbert` / `xgboost` / `knowledge_graph` / `generic_ml`；
- `minChunkChars` 同时被 `packages/retrieval/src/build.ts` 读取（见 §6），是碎块阈值的唯一来源。

## 5. 断言与复跑

```bash
# 语料校验（含领域纯度断言：excludedDocs 零命中，excludedTables 必须为 0）
pnpm exec tsx scripts/validate-corpus.ts

# 单元测试（含规则层 7 例 + 碎块阈值 2 例）
pnpm exec vitest run --root scripts validate-corpus
```

`validate-corpus` 的判定逻辑：

1. `tables.json` 每行的 `sourcePath` 若命中 `excludedDocs` 的任一条 → **报错**，错误信息带行数、`sourcePath`、`category` 与 `reason`；
2. 明细写入统计字段 `stats.excludedTables`，清洗完成后必须为 **0**；
3. 规则文件本身不合规（`version` 不是 1、`excludedDocs` 为空、`category` 非法、缺 `reason`、`sourcePath` 缺失或重复、`minChunkChars` 非正整数）同样报错——宁可红，也不让剔除条件悄悄失效。

> 修复说明：`validate-corpus.ts` 原 CLI 守卫是 `import.meta.url === 'file://' + process.argv[1]`，在 Windows 上永不成立，
> 导致 `pnpm exec tsx scripts/validate-corpus.ts` **静默空跑并 exit 0**（验收②曾是「假绿」）。
> 现改为与 `scripts/build-index.ts` 一致的 `path.resolve(fileURLToPath(import.meta.url))` 比较，并移除了 ESM 下不可用的 `__dirname`。

## 6. <30 字碎块：根因在切块层，不在语料层

按 `packages/retrieval/src/build.ts` 的切块算法对 `data/corpus/literature-full/`（40 篇）复算：

| 项 | 数值 |
|---|---|
| 切出块数 | 7,066 |
| 块长 min / p50 / p95 / max | 15 / 619 / 662 / 774 |
| < 30 字块 | **15（0.2%）** |
| < 50 字块 | 51（0.7%） |
| < 100 字块 | 198（2.8%） |

最短块的样例：

```
[15] "## References\n."
[18] "## 2.1.1. RAP\nits."
[19] "## Limitations\nNone"
[20] "## 4. Conclusions\nt."
```

这些是**章节标题 + 正文残留句**（`.` / `t.` / `its.`），在 40 个 `.md` 里手工删既费力又不解决根因。
真正的根因是切块器的下限写死在 `build.ts` 的 `text.length < 10`。

处理方式：把下限抽成 `cleaning-rules.json` 的 `minChunkChars`（本仓库 = 30），由 `build.ts` 读取；
**没有规则文件时退回 10，保持既有行为不变**（因此不影响任何既有测试与 fixture）。

效果已用单测锁定：同一份含 20 字章节残留的语料，带规则时切出 1 块，无规则时切出 2 块。

## 7. 对索引与检索的影响

- 索引块数会变化（表格 -107，文献全文按 30 字下限再减少少量碎块）；
- **本文不预设新总数**：按 T15 验收④，语料变更后由 A 按 `docs/索引构建与发布.md` 的流程重建索引，
  重建完成后以 `manifest` 的实际计数为准，并复跑检索金标准（38 条，dev 28 + held-out 10，混合 mean recall@5 ≥ 0.9187）；
- 在 A 重建之前，任何引用「11,143 块」的文档都应视为**上一次索引的旧值**。

## 9. 已知局限

1. 判据是**论文级**（整篇 `sourcePath` 进出），不是表格级的语义判定：同一篇域内论文里若有个别域外表，仍会保留；
2. 域内/域外边界的少数案例（如把 ML 用于沥青性能预测的论文）按「研究对象是不是沥青」保留，属人工判断，已在 §2 记录口径；
3. `literature-full` 的正文残留（`.` / `t.` 之类）只在切块时被丢弃，**源 `.md` 未改动**，语料本身仍含噪声；
4. 未做 OCR 噪声抽检（属 T22 chunk 质量报告的范围）。
