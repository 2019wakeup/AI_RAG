# 数据来源与清洗说明

> **一句话**：语料的**唯一真相源**是仓库内的 `data/corpus/`；向量索引由 `pnpm build:index` 可重建生成（**不入库**），因此「数据从哪来、怎么切、怎么清洗、有哪些坑」全部以本文档为准。
> **配套**：[data/corpus/README.md](../data/corpus/README.md)（目录与文件格式）｜[NOTICE.md](../NOTICE.md)（版权与再分发限制）｜[复现指南](复现指南.md)（命令）｜[选题与项目边界](选题与项目边界.md)（范围）｜[文献清单索引](data/文献清单索引.md)（149 条题录的逐条 DOI 溯源）

## 0. 语料总览

索引口径（`data/index/manifest.json`）：**11,143 块 / 395 文档**，嵌入模型 `Xenova/multilingual-e5-small`（384 维），pipelineRev 记录构建时的 git 短 SHA。

|---|---|---|---|---|---|---|

> 有三份文件**不进索引**，但属于语料目录的一部分：
> - `data/corpus/scene-tags.json`：27 个场景标签（气候 6 / 交通 4 / 病害 9 / 约束 8），用于知识条目文本的场景中文标签映射；

## 1. 材料知识条目（`knowledge`，42 文档 / 94 块）

| 项 | 说明 |
|---|---|
| **来源类型** | 项目组依据规范条文与代表性论文人工整理的「材料—性能关系」知识条目（非抓取、非原文） |
| **可追溯凭证** | 每条有 `sourceRef`；每条关系另有 `sourceRef`（DOI 或规范号）。实测 32 条条目级 sourceRef 为 DOI、10 条为规范号 |
| **规模** | 42 条，5 类：`binder` 9 / `modifier` 4 / `gradation` 7 / `additive` 11 / `mixture` 11；共 94 条关系 |
| **切分规则** | 每个 `relations[]` 关系切一块：`名称（规格）｜属性：效应；幅度。适用场景：<中文场景标签>。依据：<sourceRef>`；`docId = k-<category>-<nnn>`，`chunkId = docId:ri`；`tags` = 条目标签 + 场景标签 + `dim-<属性>` |
| **清洗与无效值处理** | ① `id` 必须匹配 `k-<category>-<nnn>` 且前缀与 `category` 一致；② `relations[].property` 必须在关系属性词汇表内（`高温PG/低温PG/疲劳/水稳TSR/E*/成本/碳排/抗滑…`），否则校验失败；③ `sourceRef` 非空；④ 场景标签必须存在于 `scene-tags.json`；⑤ 条目缺 `relations` 时退化为 `text` 单块（当前 0 条） |
| **已知问题** | **是二次加工文本，不是原文**：作证据时应能看出「这是整理文本」；不应作为「返回原始证据片段」的演示样本 |

## 2. 规范条文（`standard`，8 文档 / 57 块）

| 项 | 说明 |
|---|---|
| **来源类型** | 8 部规范的条文**摘编**（人工整理自扫描件 OCR，关键数值与表格已核对提取稿） |
| **可追溯凭证** | 文件名即规范号；分节标题格式 `## <规范号>-<条号> <主题>` |
| **规模** | 8 部 / 57 条：JTG D50-2017（9）、JTG F40-2004（7）、JTG 3410-2025（5）、JTG 5142-2019（7）、JTG 5210-2018（5）、JTG 5421-2018（5）、AASHTO HM-40（G3，12）、AASHTO HM-41（E1，7） |
| **切分规则** | 每个 `## ` 分节一 chunk：`text = ## <条号> <主题>\n<正文>`；`docId = 文件名去扩展名`（如 `jtg-d50-2017`），`chunkId = docId:idx` |
| **清洗与无效值处理** | ① 只收录与材料选型、性能要求相关的条文；② 若文件没有 `## ` 分节标题，`build-index` 直接报错（入库前先跑 `pnpm eval:corpus`）；③ 条文正文中引用的规范表格（如「表 4.5.4」）**不在语料内**，仅保留文字说明 |
| **已知问题** | ① 是**摘录**而非全文，覆盖度有限；② AASHTO 两部为「试验方法编号速查 / 勘误要点」摘编，条文数少；③ 工程引用须以正式出版物为准（见 [NOTICE.md](../NOTICE.md)） |

## 3. 论文题录（`literature`，142 文档 / 142 块）

| 项 | 说明 |
|---|---|
| **来源类型** | 文献调研表格（xlsx「全部文献」表）经 `scripts/convert-literature.ts` 转换的**题录**，无正文 |
| **可追溯凭证** | `doi` 109 条；无 DOI 的 33 条以 `sourceRef = 期刊/会议名, 年份` 兜底（保证 `sourceRef` 非空） |
| **规模** | 142 条；`docId = lit-<3 位序号>`（如 `lit-001`） |
| **切分规则** | 一条一 chunk：`标题。作者：…。期刊：…。年份：…。内容：<中文任务摘要>。DOI：…` |
| **清洗与无效值处理** | ① `（无 DOI）`、`无`、`-`、空串等占位统一按「无 DOI」处理；② 表头必需列（序号/标题/DOI）缺失即报错；③ 每条缺 `id`/`title` 即报错；④ 年份/作者缺失时该字段不拼接（不写空串） |
| **已知问题** | **只有题录、没有正文**，不能当作「原文证据」；演示与报告时应优先使用 `standard` / `literature-full` / `table` 三类原文语料 |

## 4. 论文全文（`literature-full`，40 文档 / 9,753 块）

| 项 | 说明 |
|---|---|
| **来源类型** | 已获取的论文 PDF，经 **MinerU 离线解析**为 Markdown 的节选副本（原始 PDF 与解析中间产物 `literature_md/` 均不入库） |
| **可追溯凭证** | 每个 `.md` 文件头有 `<!-- SOURCE: 原始 PDF: <路径> \| 页数: n \| 集合: … 题录: … (DOI: …) -->`；40 篇中 32 篇可提取到 DOI，其余为无 DOI 或题录缺失 |
| **规模** | 40 篇 / 9,753 块；文本约 4.1 MB；`docId = litfull-<序号>`（两个 `litfull-nolit-…` 文件名含题名，同样作为 docId） |
| **切分规则** | ① 去掉整行图片引用（`![](images/…)`）；② 按 `## ` 分节；③ 节内按空行分段落装包，目标 **~500 字**、硬上限 **600 字**，单段超长按 600 硬切；④ 丢弃 `<10 字` 的碎块；⑤ `chunkId = docId:idx` |
| **清洗与无效值处理** | 无标题文档整体当一节切；图片不随仓库（`images/` 不入 corpus）；OCR 噪声不做逐字校订，仅保证切块可用 |
| **已知问题** | ① 少数章节块 **<30 字**（OCR 噪声或短标题段），证据价值低（E 的 T16 过滤）；② 公式/表格在 MinerU 转换中有损耗；③ **chunk 无 overlap**，跨块语义可能被切断；④ 是**节选**，不是整篇入库 |

## 5. 定量表格（`table`，107 文档 / 1,041 块）

| 项 | 说明 |
|---|---|
| **来源类型** | 论文（及部分规范）中的含数值表格，由 `scripts/extract-tables.ts` 从 MinerU `structured_content.json` 递归提取 |
| **可追溯凭证** | 每条含 `docTitle` / `caption` / `page` / `sourcePath`；表格块文本带「来源：<论文题名>」 |
| **规模** | 1,041 张表 / 107 个表文档 docId（对应 85 个不同论文题名）；`docId = table-<docSeq>`（同一文档多表共用一个 docId），`chunkId = table-<docSeq>-<idx>` |
| **切分规则** | 一表一 chunk：`text = <表题>｜来源：<论文题名>｜<Markdown 前 1,200 字>`；`tags` 由表题与论文题名的关键词映射（车辙/低温/疲劳/水稳/掺量/RAP/级配/模量/空隙率/碳排…） |
| **清洗与无效值处理** | ① 只保留含数值（正则 `\d`）且长度 ≥20 的表；② 空表/纯图片表过滤；③ `caption` 为空时用「文档标题 表 <序号>」兜底；④ 页码取所属 `pages` 下标 +1（不用 bbox 推算） |
| **已知问题** | ① 约 **12%（约 128 / 1,041）** 的表格来自域外文献（LLM/知识图谱/DPR/XGBoost 等方法类论文），需物理剔除（E 的 T15）；② 单表 Markdown 截断到 1,200 字；③ 同一文档多表共用 docId，文档级指标要去重 |

## 7. 数据划分声明（防「自己出题自己判卷」）

### 7.1 无训练过程

本系统**不训练任何模型**：嵌入模型是预训练模型（e5-small / bge-m3），LLM 通过 API 调用，检索与生成都是推理。因此：

- **没有 train / val / test 划分**；
- **没有训练集/验证集**，也不存在「用评测集调参」之外的超参数搜索；
- 唯一需要防止的是「评测集与语料同源」这一闭集风险（见 §7.4）。

### 7.2 三个评测集，互不复用

| 评测集 | 文件 | 规模 | 用途 | 指标 |
|---|---|---|---|---|
| **检索金标准** | `data/golden/golden.json` | 38 条查询 / 91 个期望文档 | 检索能力回归（三方案对比） | doc 级 recall@5（达标条数 + 均值）；micro 口径 82/91 |
| **QA 金标**（待建） | `data/golden/qa.json` | 24 条：正样本 16 + 负样本 8 | 问答端到端：答案正确率、引用正确率、拒答准确率 | 见 [任务拓扑](plan/task-topology.md) T23、T24、T26 |
| **端到端案例** | `data/corpus/cases/cases.json` | 5 个场景案例 | 推荐链路端到端断言（候选数/证据/雷达/确定性/降级） | 全部断言通过（`pnpm e2e`） |

互不复用的约定：

1. 38 条检索金标准的 `query` 文本**不得**直接复制为 QA 金标问题；QA 金标问题独立编写，允许命中同一批文档。
2. 5 个端到端案例的场景**不得**作为 QA 金标问题（避免用推荐链路的输入充当问答输入）。
3. QA 金标的负样本必须覆盖 3 类：**域外问题**（如天气/股票）、**域内但语料无覆盖**（如未公开配方）、**信息不足需追问**（如「该用什么沥青」缺场景），三类各 ≥4 条（共 8 条）；正样本 16 条只取 `standard` / `literature-full` / `table` 三类原文语料，**不得取** `knowledge` / `enterprise` 二次加工语料（否则「引用原文」不成立，见 T23）。
4. QA 金标与检索金标准按 [T24](plan/task-topology.md) 划分：检索金标准 **38 条 → dev 28 / held-out 10**，QA 金标 **24 条 → dev 16 / test 8**；held-out 不参与调参，报告口径为「dev 28/28 + held-out 10 条单独报告」。

### 7.3 检索金标准的构成

- 38 条用例按语料类型分组：`knowledge` 13 条、`standard` 10 条、`literature` 15 条；
- 每条含 `query` / `expectedDocIds`（文档级期望，共 91 个）/ `minRecallAt5` 门槛；
- 评测口径：取 `topK×3` 命中后按 `sourceDocId` 去重，截前 5 个文档，`recall@5 = 命中期望文档数 / 期望文档数`。

### 7.4 闭集评测声明（报告中必须写）

- 91 个期望文档**全部在索引内**（闭集），因此金标准数字反映的是「已知语料上的检索质量」，不能外推为开放域能力；
- 门槛 `minRecallAt5` 中有 18 条为 1.0，存在「按现有结果标定门槛」的风险；换模型/换索引后**不保证** 38/38；
- held-out 划分由 [T24](plan/task-topology.md) 落地：检索金标准 **dev 28 / held-out 10**、QA 金标 **dev 16 / test 8**；**当前尚未执行**，报告须如实说明「现阶段 38 条全量参与回归」，并把「达标条数」与召回率（mean recall@5）分开表述。

## 8. 数据入库流程（可重建缓存）

```
data/corpus/（真相源，入库）
   │  pnpm build:index（或 POST /api/v1/kb/rebuild，同一套代码）
   ▼
① 6 类语料切块（knowledge/standard/literature/literature-full/table/enterprise）
   ▼
② contentHash = sha256(text)，chunkId = docId:chunkIdx
   ▼
③ 与 data/index/manifest.json 对比：新增嵌入 / 内容变化重嵌 / 语料删除同步删除 / 未变跳过
   ▼
④ 嵌入（e5 系列自动加 query/passage 前缀；EMBEDDING_PREFIX_MODE=off 可关）
   ▼
⑤ 写入向量库：LanceDB（data/index/lancedb）或 SQLite（data/index/app.db）
   ▼
⑥ manifest 落盘：embeddingModel / modelVersion / dim / pipelineRev / 每块 contentHash
```

要点：

1. **幂等**：同样内容重复构建不会重复写入（`added=0 skipped=N`）；内容变化只重嵌变化块；语料删除会同步删块。
2. **强制全量重建**的触发条件：`--rebuild`；**换嵌入模型**（`modelName` / `modelVersion` / `dim` 任一变化）；manifest 与向量库数量不一致（`storeLost`）。这是防止「旧向量 + 新查询」静默漂移的防线。
3. **provenance 7 字段**随块入库：`sourceDocId / contentHash / embeddingModel / modelVersion / dim / pipelineRev / embeddedAt`，任何检索结果都能追溯「哪篇文档、哪次构建、哪个模型」。
4. **索引不入库**：`data/index/`（LanceDB 索引约 110 MB）与模型缓存 `data/index/hf-cache/`（首次下载，e5-small 约数百 MB，取决于所选模型）均被 `.gitignore` 排除；新仓库首次运行必须构建索引（实测约 **729 s**，11,143 块，e5-small）。
5. **关系库自动种子**：服务启动时若 `data/db/relation.db` 为空，会从 `data/corpus/` 自动种子；该库同样不入库。
6. **校验前置**：入库前跑 `pnpm eval:corpus`（`scripts/validate-corpus.ts`），当前输出 `ok=true`、42 条目 / 94 关系 / 5 案例 / 27 标签 / 8 规范 / 57 条文 / 142 文献。
7. **索引指纹**：T04 落地后由 `pnpm exec tsx scripts/build-index.ts --check` 生成 `docs/experiments/index-fingerprint.json`（`count / model / dim / manifestHash / pipelineRev / command / generatedAt`），用于核对本地重建与基线是否一致；在此之前以 `data/index/manifest.json` 的块数与 `dim` 为准。

## 9. 已知问题汇总

| # | 问题 | 影响 | 处理计划 |
|---|---|---|---|
| 1 | `tables.json` 约 12%（约 128/1,041）表格属域外文献 | 「明确领域」论证被稀释；检索可能返回无关表格 | E·T15 物理剔除 + 在本文档记录筛选标准 |
