# 团队分工说明

> **适用**：课程设计「带证据引用与可信拒答的领域知识库问答系统」提交材料（公开仓版本）。
> **配套**：任务编号与写域以 [`docs/plan/task-topology.md`](plan/task-topology.md) 为准，机器可读版在 [`docs/plan/tasks.json`](plan/tasks.json)。本文回答「谁负责什么、为什么这样切、出了事找谁」。
> **基线**：仓库底座迁移由 **成员 A** 完成（**M0 基线提交**，`main` 初始 commit；已交付清单见 [`docs/plan/task-topology.md` §0.5](plan/task-topology.md)），含 Vue3 + Hono + pnpm monorepo 迁入、QA 契约与 501 骨架、CI 三段门禁、`pnpm test` **334 passed / 3 skipped**。**本表描述的是 M0 之后的全部工作归属**。

---

## 1. 分工原则

1. **一人一写域**：每个成员拥有互不重叠的目录/文件集合，冲突在物理上被消除，而不是靠「沟通着点」。
2. **一任务一 PR**：每个任务对应一个 Issue、一个 PR（`L` 级允许拆 1–2 个 PR），单 PR ≤ 400 行 diff。
3. **共享文件只由 A 改**：`packages/contracts/src/schemas.ts`、`apps/server/src/app.ts`、`apps/web/src/router.ts`、根 `package.json`、`apps/server/src/config.ts`、`data/index/**`、`.github/**`。其他人需要改动 → 在 Issue 登记 + A 评审。
4. **接口靠契约、不靠口头**：B（问答链路）与 C（可信拒答）之间的唯一接口是**两个纯函数签名**（`decideRefusal() → {refused, reason, confidence}`、`collectNeedInfo() → string[]`）+ 契约里的 `refused / refusalReason / needInfo` 三字段。接入动作由 B 在 `index.ts` 里做（T19），C 从不改 B 的文件。

## 3. 逐人说明（含答辩可被提问的 3 个技术点）

> 答辩时评委通常挑「你亲手写的那个文件」追问，所以每人的 3 个技术点都落在**自己写域里的具体实现**上，全部可以在仓库里指到行。

### A｜平台与集成
- **交付**：M0 基线提交（§0.5 清单）+ T01–T05、T07；合入门禁与 CODEOWNERS。
- **答辩技术点**
  1. **为什么把 QA 契约放在 `packages/contracts` 而不是前后端各写一份？** 说清 `QaResponse` 的字段设计（`answer` / `citations[].n + snippet` / `refused` / `refusalReason` / `needInfo` / `status` / `trace`），以及两个纯函数签名如何成为 B 与 C 之间「不互相改文件」的唯一接缝；破坏性变更需新 Issue。
  2. **RRF 融合分为何不能直接当拒答判据？** RRF 是排名倒数加和，分值与相关度不同量纲；拒答必须用原始相似度（余弦 / BM25 原始分）与覆盖率，这也是 `config/params.json` 里阈值分组的由来。
  3. **三份索引产物（评测脚本用的 `app.db`、服务端 sqlite 后端用的空库、以及全量的 lancedb）为什么必须统一成一个口径？** 讲 `manifest` 的 `dim / modelVersion / pipelineRev` 如何防止「用 e5-small 建的索引配 bge-m3 查询」的静默错配，以及 `build-index --check` 的校验项。

### B｜问答链路后端
- **交付**：T08–T11（问答链路）+ T19（把 C 的拒答/追问接入编排）；端点 `POST /api/v1/qa` 与 `/api/v1/qa/stream`。
- **答辩技术点**
  1. **答案里每个断言怎么绑定到 `[n]`？** 讲生成后的双向校验：`[n]` 必须落在 `citations` 区间内、越界编号被剔除；prompt 里「只依据给定 chunk 作答」如何与 `insufficient:true` 配套。
  2. **证据选择为什么先取 topK×3 再按 `sourceDocId` 去重取前 k？** 讲同一文档多 chunk 挤占名额造成的假性失分，以及 6 类 docType 的配额（`orchestrator.ts:831-872` 复用）如何保证证据多样性。
  3. **LLM 不可用（HTTP 402）时为什么走「抽取式降级」而不是 5xx 或硬拒？** 讲降级语义：拼接证据原句 + `status:"degraded"`、SSE 末帧必须发 `done` 而不是挂起、端到端 < 2s 的验收线；以及 T19 里如何在 `index.ts` 调 C 的纯函数而不改 `refusal.ts`。

### C｜可信拒答策略
- **交付**：T17 / T18 / T20 —— `refusal.ts`（判据 + 置信度）、`clarify.ts`（追问）、`refusal-eval.ts`（拒答矩阵）。
- **答辩技术点**
  1. **四条判据的优先级为什么是 `insufficient_evidence > low_relevance > no_hit`（`llm_unavailable` 单列）？** 讲「宁可拒也不编」的取向：LLM 自己说答不了是最强信号，命中数是最后兜底；并说明为什么判据必须是可单测的纯函数、阈值只能来自 `config/params.json`。
  2. **拒答与追问的边界在哪？** 域外问题 / 无命中 → 拒答；域内但缺必填槽位（场景、气候分区、交通等级、病害类型）→ `needInfo` 追问。「该用什么沥青」为什么不硬拒。
  3. **拒答准确率怎么算才不算自欺？** 讲混淆矩阵四格、三类负样本（域外 / 域内无覆盖 / 信息不足）的构造，以及为什么样本不足时必须打印「样本不足」而不是记 0 分。

### D｜前端问答体验
- **交付**：T12–T14、T21，`/qa` 视图与角标定位。
- **答辩技术点**
  1. **`[n]` 角标怎么定位到原文？** 讲 `data-evidence-id` 选择器 + `useEvidenceAnchor` composable（从 `RecommendView.vue:234-259` 抽出）、700ms flash + toast 的微反馈，以及为什么要抽 composable 而不是复制一份逻辑。
  2. **拒答/追问/空态四态为什么要独立组件 + 集中文案？** 讲「不出现『出错了』」的文案策略（`copy.ts` 单一来源、与 `refusalReason` 枚举一一对应），以及追问表单提交时 payload 如何带槽位二次提问。
  3. **前端类型为什么全部从 `@ai-rag/contracts` 导入？** 讲契约变更时前端在 `pnpm typecheck` 阶段就报错，而不是运行时空字段；举 T07 给 `QaResponse` 加字段时的连锁效果。

### E｜数据与语料治理
- **交付**：T15 / T16 / T23 / T24 —— 语料清洗 + 数据卡 + 24 条 QA 金标 + dev 28 / held-out 10 划分。
- **答辩技术点**
  1. **怎么判定一条表格块「域外」？** 讲以 `sourcePath` 为键的可复跑规则（LLM agent / DPR / ColBERT / XGBoost / 知识图谱 / 通用 ML 六类）+ 人工抽样，剔除 24 篇 / 107 张表（1,041 → 934），并用 `validate-corpus` 断言零残留；为什么必须物理剔除而不是只在文档里声明——这是题面「选择一个明确领域」的直接证据。
  2. **金标为什么只用 `standard / literature-full / table`？** 讲证据成色分层：`literature`（142）只有题录、`knowledge`（94）与 `enterprise`（56）是模板二次加工，靠它们满足不了「返回原始证据片段」。
  3. **held-out 划分解决了什么问题？** 讲「自己出题自己判卷」：检索金标 38 条留出 10 条、QA 金标 24 条拆 dev/test，以及 6 条用例 recall 恰好等于门槛的可疑现象怎么处理。

### F｜评测与实验
- **交付**：T06、T25–T28，四档检索对比 + qa-eval + 三项消融 + 报告。
- **答辩技术点**
  1. **「38/38 达标」为什么不等于 100%？** 讲达标条数 vs mean recall@5 = 0.9187、doc 级 micro = 82/91 = 0.9011，以及报告里为什么必须写「达标 38/38，均值 0.919」。
  2. **recall@5 / MRR@10 / nDCG@10 各回答什么？** 讲重排评估为什么要固定候选池（hybrid top-20）再比较，否则结论被检索上限掩盖；以及纯向量档为什么可以零后端改动（`store.search({text:'', vector})`）。
  3. **LLM 缺额时指标为什么写 `llm: null` 而不是 0？** 讲「0 分」与「未配置」的语义差别、裁判与生成同厂商的局限，以及 402 时哪些结论仍可复现（检索、拒答规则判据）与哪些必须推迟（引用支撑率、幻觉率、重排时延）。

## 4. Git 署名与 PR 归属规范

### 4.1 三种手段（按优先级）

1. **PR 归属（主要手段）**：每个任务由一个成员的 GitHub 账号开分支、提 PR；PR 的 `Files changed` + `Commits` 页即归属证据。CODEOWNERS 里的 `@OWNER-<X>` 与该成员账号对应。
2. **`Co-authored-by`（协作提交）**：结对或代提交时，在 commit message 末尾加 trailer，**不写真实姓名**，用代号 + GitHub noreply 邮箱：
   ```
   feat(qa): 接入拒答判定并透出置信度

   Co-authored-by: member-c <member-c@users.noreply.github.com>
   ```
   合入时用 rebase-and-merge（或 squash 时在最终 commit message 保留该 trailer），保证 `git log` 可检索到协作痕迹。
3. **团队账号兜底**：仅当成员账号不可用时，由团队账号提交，并在 PR 正文写「本次提交代 member-x 推送，对应任务 T19」，同时保留 `Signed-off-by: member-x`。

### 4.2 具体做法（可直接照抄）

| 场景 | 做法 |
|---|---|
| 单人任务 | 用自己的账号 → 分支 `feat/T19-refusal-wiring` → PR 标题 `[T19] 拒答接入流水线（接缝由 B 提供）` → 正文 `Closes #<issue>` |
| 结对 / 代提交 | 提交人 + `Co-authored-by: member-<x> <member-<x>@users.noreply.github.com>` |
| 首轮 CODEOWNERS | `@OWNER-A` … `@OWNER-F` 为占位句柄；**首次合并前由 A 统一替换为真实 GitHub 用户名**（或组织 team 句柄 `@<org>/<team>`） |
| 署名禁止项 | 真实姓名、学号、学校邮箱、个人手机号、身份证/住址信息，一律不出现在 commit / PR / Issue / 文档里 |

### 4.3 为什么仓库内不写真实身份

1. **这是公开仓库**：commit 与 PR 会被搜索引擎与第三方长期索引，写进去就撤不回（GitHub 的历史改写成本极高）。真实姓名 + 学校 + 邮箱组合足以定位到个人。
2. **大赛材料要求匿名**：项目同时用于参赛包，赛制要求匿名评审；一旦真实身份进入 git 历史，匿名包与实名包就无法从同一仓库干净拆出。
3. **课程材料需要实名**：课程提交包（非公开、离线 zip）里放实名分工表与答辩名单，由课程方在本地映射。两套材料**分目录打包**，仓库只保留代号版本。
4. **可追溯性不受损**：归属证据靠「PR 作者 + CODEOWNERS + `Co-authored-by` trailer + Issue 认领」四件套，足够区分每个人写了什么，不需要写真实姓名。

> 映射表（A–F ↔ 实名）**只存在于课程提交包**，由班级/课程方保管。仓库内任何文件出现真实身份即视为违规，PR 不予合入。

## 5. 认领与交接

1. **认领**：Issue 由 `docs/plan/tasks.json` 生成后，成员在 Issue 下评论「claim」并把自己设为 assignee；同一 Issue 同时只有 1 个 assignee。
2. **交接**：任务换人 → 在 Issue 里写「由 X 转交 Y，已完成部分见 PR #n」，并请 A 在 `tasks.json` 与 `task-topology.md` 同步更新 `owner`。
3. **阻塞申报**：卡住超过 0.5 个工作日 → Issue 打 `blocked` label 并写明阻塞点（如「LLM 402，等额度」）；未申报的延期视为排期问题而非阻塞。
4. **验收**：每个 PR 必须由至少 1 名非作者评审；涉及共享文件由 A 评审；最终由 A 合入。
